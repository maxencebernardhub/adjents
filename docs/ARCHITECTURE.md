# Adjents — Architecture

This document is the reference architecture for Adjents v0.1. It captures not only
*what* was decided but *why* — so future contributors (or a future version of the
team) can understand the reasoning before changing anything.

Each significant architectural change should be accompanied by an ADR in
`docs/decisions/` explaining context, alternatives considered, and consequences.
This document is updated to stay in sync.

## 2. No AI framework — building from scratch

We explicitly chose **not** to use LangChain, LangGraph, LlamaIndex, CrewAI, or
AutoGen for the agent logic. Here is why.

**LangChain / LangGraph**: Widely used but notorious for leaky abstractions and
high friction. LangGraph models agent workflows as explicit graphs — the exact mental
model we want to hide from users. Coupling our internal architecture to LangChain
would make future changes harder, not easier.

**LlamaIndex**: Focused on RAG pipelines and data connectors. Useful for the memory
layer but overkill — Chroma's Python client does what we need in ~20 lines.

**CrewAI / AutoGen**: High-level multi-agent frameworks. Their abstractions (crew,
task, role) are appealing on paper but conflict directly with our design: agent loop
as an asyncio coroutine, typed async message bus, N-level hierarchy, PixiJS visual
state. Fitting our architecture into their model would cost more than building our own.

**What we use instead**: the official SDKs for each LLM provider, plus focused
libraries for specific sub-problems.

| Need | Library | Why |
| --- | --- | --- |
| Anthropic LLM calls | `anthropic` (official SDK) | Native tool use, streaming, prompt caching |
| OpenAI LLM calls | `openai` (official SDK) | Standard |
| Google LLM calls | `google-genai` (official SDK) | Standard |
| Ollama calls | `httpx` (async HTTP) | Ollama exposes a simple REST API |
| Vector database | `chromadb` | Local-first, no server required |
| SQLite ORM | `sqlmodel` | Pydantic + SQLAlchemy, matches our stack |
| Async SQLite driver | `aiosqlite` | Non-blocking SQLite access in asyncio coroutines (see ADR 0003) |

**`AnthropicClient` — streaming unconditionally**: `AnthropicClient.complete()`
always uses `messages.stream()` + `get_final_message()`, regardless of `max_tokens`.
The Anthropic SDK refuses a non-streaming `messages.create()` whose expected
duration (`3600 × max_tokens / 128000` seconds) exceeds 10 minutes — i.e. above
~21,333 `max_tokens`, for every model (its `MODEL_NONSTREAMING_TOKENS` table only
adds a lower 8192 cap for Opus 4.0 / 4.1). With Claude 5.5 models thinking is always
on and shares the output budget, so `GeneratorOrgGeneration` uses
`_MAX_TOKENS = 64000`. Streaming unconditionally removes this ceiling with a single
code path. See ADR 0007 (amended 2026-10-22).

**LLM call contract**: callers only see a provider-neutral contract — a required
`effort` (`low` / `medium` / `high`), a `max_tokens` guardrail, a `str` result, and
typed errors for unusable responses (`LLMRefusalError`, `LLMTruncatedError`,
`LLMResponseError` in `llm/errors.py`). `AnthropicClient` checks `stop_reason`
before reading any text and sends explicit adaptive thinking with summarized
display. The OpenAI and Gemini clients of step 10 implement the same contract.
See ADR 0012.

The agent loop, message bus, router, and scheduler are written from scratch, as
small single-responsibility modules (300 lines = review trigger, 500 = hard limit —
see `.claude/CLAUDE.md`). We keep full control and avoid dependency lock-in.

## 3. Core data models (Pydantic v2)

**Why Pydantic v2**: Pydantic is already the validation layer for FastAPI. Using it
for all data contracts means one system handles validation, serialization, and type
safety across the entire backend. No impedance mismatch between the API layer and
the business logic layer.

### Agents are data, not code

**What "agents as code" would mean**: one Python class per agent, each with its own
hard-coded behavior — `class FinanceAgent(BaseAgent)` overriding a `think()` method
with finance-specific logic, `class SalesAgent(BaseAgent)` with another, and so on.
This is the usual shape of hand-built multi-agent systems, where the developer knows
the team in advance.

**Why it is impossible here**: in Adjents, agents do not exist before onboarding.
The Generator Agent (an LLM) invents the org at runtime, from the user's interview:
one user gets a "Wedding Planning Lead", another a "Grant Applications Specialist".
No class can be written in advance for an agent nobody knows yet. The only way to
keep "one class per agent" would be to have the LLM generate Python code and execute
it — a major security risk (arbitrary code running on the user's machine), and code
that is untested, untyped and unreviewed.

**What an agent is instead**: a set of records, all keyed by the agent's `id`:

- one `AgentSpec` row in SQLite — identity, role, responsibilities, hierarchy
  position, schedule (see below);
- its `Skill` rows (`skill_ids`);
- one `AgentState` row — runtime status;
- one namespaced Chroma collection — its memory (§7).

Prompts are shared templates per agent type (`prompts/agent/`, `prompts/coo/`),
rendered with the agent's fields. Behavior comes from one generic agent loop (§5)
that reads these records and feeds them to the LLM.

**Impact**:

- Creating an agent = inserting rows. The Generator Agent outputs JSON, validated
  by Pydantic, then persisted — no code is generated, nothing is executed.
- Reconfiguring an agent (ADR 0009) = a SQL `UPDATE`. No redeploy, no restart.
- One agent loop to write, type-check and test, whatever the size of the org.

**Trade-offs**:

- Every behavioral difference between agents must be expressible through fields,
  prompts and skills. There is no escape hatch for bespoke per-agent logic.
- The weight of agent quality rests on prompt engineering and on the quality of the
  generated specs, not on code.
- Special cases are expressed as data, never as a subclass. Example: the COO is an
  ordinary `AgentSpec` with `level == 0`; its specific behavior comes from its
  prompts (`prompts/coo/`) and from code paths that branch on `level`, not from a
  `COOAgent` class.

See ADR 0010.

### `AgentSpec`

The static definition of an agent. Generated by the Generator Agent. Fully
serializable and stored in SQLite.

```python
class AgentSpec(BaseModel):
    id: str                          # UUID
    name: str                        # e.g. "Finance Lead", "Alex"
    level: int                       # 0 = COO, 1 = N-1, 2 = N-2, etc. No upper bound.
    parent_id: str | None            # None for the COO
    domain: str | None               # "Sales", "Finance", "HR"... None for COO
    role_description: str
    responsibilities: list[str]
    skill_ids: list[str]             # v0.1: descriptive only; v0.2: executable
    escalation_rules: list[str]
    scheduler_interval_seconds: int  # Autonomous wake-up interval
    work_hours: str | None           # e.g. "09:00-18:00"; None = always active
    is_paused: bool                  # User-controlled pause
    visual_character: str            # Sprite identifier for the PixiJS workspace
    created_at: datetime
```

`level` is an integer with no upper bound.

`visual_character` must be one of a predefined set of valid sprite identifiers (e.g.
`"character_suit"`, `"character_creative"`, `"character_tech"`...). The full list is
injected into `prompts/generator/org_generation.md` so the LLM picks semantically from
available sprites. A free string would point to a non-existent sprite file and break
the PixiJS workspace. The user can change their agents' sprites during the post-generation
validation conversation (ADR 0006). We deliberately avoided
`Literal["N0", "N1", "N2"]` because the VISION specifies no hard cap on hierarchy
depth — a complex business may have N-3 or deeper agents.

**Restructuring safety (v0.1 constraint)**: `GeneratorOrgGeneration.generate()` always
persists with plain INSERT — never a DELETE + INSERT. Agents removed during a future
restructuring are marked inactive rather than deleted, so their memory (Chroma
collections, SQLite records) survives. An `is_active: bool` field will be added to
`AgentSpec` in v0.2 when restructuring is implemented. See ADR 0005.

### `AgentState`

The **runtime** state of an agent. Separated from `AgentSpec` because spec and state
change at very different rates: a spec is written once at onboarding; a state changes
many times per minute. Keeping them separate avoids constant overwrites of the full
spec record.

```python
class AgentStatus(StrEnum):
    IDLE = "idle"
    WORKING = "working"
    IN_MEETING_1ON1 = "meeting_1on1"
    IN_MEETING_GROUP = "meeting_group"
    PAUSED = "paused"
    WAITING_FOR_HUMAN = "waiting_for_human"

class AgentState(BaseModel):
    agent_id: str
    status: AgentStatus
    current_task_summary: str | None
    meeting_with: list[str]          # Agent IDs if in a meeting
    updated_at: datetime
```

`AgentState` is stored in SQLite and broadcast via WebSocket on every change. The
PixiJS workspace and the org chart view both consume it.

`AgentState` records are created by `GeneratorOrgGeneration.generate()` alongside their
corresponding `AgentSpec`, with `status = PAUSED`. This guarantees that every `AgentSpec`
in SQLite always has a corresponding `AgentState` — no orphan agents, no null checks
in downstream code (API endpoints, WebSocket, org chart view).

### `AgentValidationRecord`

One record per root agent (COO or N-1) within a `ValidationSession`. Tracks the
depth-first conversation traversal through the agent's subtree.

```python
class AgentValidationStatus(StrEnum):
    PENDING     = "pending"
    IN_PROGRESS = "in_progress"
    VALIDATED   = "validated"
    SKIPPED     = "skipped"

class AgentValidationRecord(BaseModel):
    id: str
    session_id: str
    root_agent_id: str
    status: AgentValidationStatus
    active_agent_id: str | None        # currently active agent in this subtree
    active_conversation_id: str | None
    navigation_stack: list[str]        # DFS stack; [] = subtree exhausted

    visited_agent_ids: list[str]       # agents whose conversations are closed

```

`navigation_stack`, `conversation_ids`, and `visited_agent_ids` are JSON-serialized

`TeamSetupOrchestrator` drives the depth-first traversal and calls a single extraction
LLM at `validate_team()` time to apply all adjustments in one pass. See ADR 0006 for
the full team-setup design and ADR 0008 for the extraction pattern and retry logic.

### Persistence layer — SQLModel tables (`db/`)

The Pydantic models in §3 are the **domain and API layer**: they define the data
contracts used by FastAPI responses, agent logic, and inter-module communication.
They are deliberately kept free of persistence concerns.

Persistence is handled by a **separate set of SQLModel table classes** in
`backend/adjents/db/tables.py`. Each table class mirrors a domain model but inherits
from `SQLModel` with `table=True`. Explicit conversion functions in
`backend/adjents/db/convert.py` translate between the two layers.

**Why two separate layers** (see ADR 0002 for full rationale):

- SQLModel `table=True` imposes field annotations (`primary_key`, `__tablename__`)
  that are persistence details and do not belong in the domain model.
- `list[str]` and `dict[str, Any]` fields are not natively supported by SQLite.
  They are JSON-serialized in the DB layer only — the domain model stays clean.
- FastAPI uses the Pydantic models as response schemas. Mixing SQLModel internals
  into those models would bleed persistence details into the API contract.

### Fields requiring serialization

Two types of fields require explicit serialization in the `db/` layer:

**`datetime` fields** are stored as ISO 8601 strings (`datetime.isoformat()`) in all
table classes. `datetime.fromisoformat()` (Python 3.11+, timezone-aware) restores them
on read. This avoids SQLAlchemy's default behavior of stripping timezone info from
SQLite `DATETIME` columns.

**`list[str]` and `dict[str, Any]` fields** are stored as JSON text (`json.dumps` /
`json.loads`). The table column name differs from the Pydantic field name when needed
to avoid SQLAlchemy reserved names (e.g. `metadata` → `metadata_json`).

| Model | Field | SQLite storage |
| --- | --- | --- |
| `AgentSpec` | `responsibilities`, `skill_ids`, `escalation_rules` | `TEXT` (JSON array) |
| `AgentState` | `meeting_with` | `TEXT` (JSON array) |
| `Skill` | `inputs`, `outputs` | `TEXT` (JSON array) |
| `Message` | `metadata` | `TEXT` (JSON object) |
| `Memory` | `metadata` | `TEXT` (JSON object) |
| `Conversation` | `participant_agents`, `message_ids` | `TEXT` (JSON array) |
| `Project` | `deliverable_descriptions`, `contributor_agent_ids` | `TEXT` (JSON array) |
| `AgentValidationRecord` | `navigation_stack`, `conversation_ids`, `visited_agent_ids` | `TEXT` (JSON array) |

### DB engine setup

`backend/adjents/db/engine.py` owns the SQLite engine and session lifecycle.
Sessions are **async** throughout — see ADR 0003.

```python
engine = create_async_engine("sqlite+aiosqlite:///./data/adjents.db")

async def create_db_and_tables() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(SQLModel.metadata.create_all)

async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSession(engine) as session:
        yield session
```

Called once at FastAPI startup (`lifespan`). All agent loops and API routes use
`await session.exec(...)` — no synchronous DB calls anywhere in the codebase.

## 4. Inter-agent messaging

All agent-to-agent and agent-to-user communication goes through **typed async
message passing** — never direct method calls between agents.

> **Status: not implemented yet.** The `Message` and `Conversation` models
> (`messaging/models.py`) and their tables exist. The `MessageDispatcher` described
> below does not: it lands with the agent loop. Today's user ↔ agent conversations
> (onboarding interview, team setup, reconfiguration) call the LLM directly and
> persist each turn as a `Message` row — no agent loop runs yet, so no routing is
> needed.

### What "typed message passing" means

**Message passing**: an agent never calls a method on another agent
(`finance_agent.compute_invoice(...)`). It builds a `Message` object and drops it
into the recipient's mailbox, then carries on with its own work. The recipient reads
its mailbox when it is ready. The analogy is email versus a phone call: a phone call
blocks both parties until it ends; an email is asynchronous — the sender does not
wait, and the recipient answers when it can.

**Typed**: a message is not a free-form `dict` but a Pydantic model (§3):

```python
class Message(BaseModel):
    id: str
    from_agent: str                  # agent_id, "user", or "system"
    to_agent: str                    # agent_id or "user"
    content: str
    metadata: dict[str, Any]         # routing context, tracing
    parent_message_id: str | None    # threading: the message this one answers
    created_at: datetime
```

Pydantic validates every message at runtime (a malformed message fails loudly at
creation, not three agents later), and mypy checks every producer and consumer
statically.

### Planned design: in-process async dispatcher

Each agent gets a dedicated `asyncio.Queue` (its mailbox). A central
`MessageDispatcher` routes every message:

```text
Agent A  →  dispatcher.send(message)  →  Agent B's queue
                                      →  User WebSocket (if to_agent == "user")
```

No agent holds a reference to another agent. The dispatcher is the single routing
point; agents only know IDs.

### Why not direct calls

Agents are concurrent asyncio tasks (§5), each spending most of its time waiting on
LLM calls. With direct calls:

- **Blocking**: if agent A calls agent B and awaits the result, A is stuck for the
  whole duration of B's LLM call — A cannot process its own mailbox meanwhile.
- **Deadlocks**: if A waits for B while B waits for A (e.g. a Sales lead asks
  Finance for a price while Finance asks Sales for the client's volume), both wait
  forever.
- **No trace**: a method call leaves no record. Nobody — neither the user nor a
  developer — can see who asked what.

With the dispatcher:

- **Inspectability**: every interaction is a persisted `Message` record; the UI can
  show agent conversations and meetings live (VISION §1.6).
- **Replayability**: a session can be reproduced from its message history.
- **Testability**: an agent is tested in isolation by injecting a fake dispatcher
  that records sent messages — no other agent needs to exist.
- **Async-friendliness**: no agent blocks while another is thinking.

### Trade-offs

- **Indirection**: following a flow means following messages across mailboxes,
  not reading a call stack.
- **Request/response correlation is manual**: when A asks B a question, B's answer
  arrives later as just another message. A matches it to its question through
  `parent_message_id`. A circular wait (A waits for B's answer, B for A's) is still
  logically possible, but neither agent is frozen: both keep processing their
  mailboxes, and the pending question is visible in the message log.
- **Async debugging is harder**: a bug may surface in B long after A sent the
  faulty message; message logs replace stack traces.
- **An in-memory queue is lost on crash**: an `asyncio.Queue` lives in the process.
  The dispatcher must therefore persist every message to SQLite before enqueuing
  it, so that pending messages can be re-enqueued on restart — consistent with
  "SQLite is the source of truth" (§11).

### Why `asyncio.Queue` and not an external broker (Redis, NATS)

For a local, single-user application, an in-process queue is simpler, faster, and
has zero operational overhead. The `MessageDispatcher` interface is designed to be
swappable: the transport can later be replaced by Redis Pub/Sub without changing
agent code — relevant only for a hosted, multi-tenant (SaaS) version, where agents
might run in several processes or on several machines.

## 5. Agent lifecycle and autonomous loop

### Lifecycle states

```text
[ Created by Generator Agent ]  (is_paused = True)
          │
          │  user meets each N-1 agent 1-on-1 (or skips)
          ▼
      [ IDLE ]  ←──────────────────────────────┐
          │                                     │
          │  scheduler fires OR message arrives │  task complete / nothing to do
          ▼                                     │
     [ WORKING ] ────────────────────────────── ┘
          │
          │  needs human decision
          ▼
  [ WAITING_FOR_HUMAN ] ── user responds ──→ [ WORKING ]
          │
          │  user clicks pause
          ▼
      [ PAUSED ] ── user resumes ──→ [ IDLE ]
```

Agents are created with `is_paused = True`. They transition to `IDLE` after the user
meets each N-1 agent one-on-one (or explicitly skips the step). These conversations are
between the user and each N-1 agent directly — not with the Generator Agent. Each N-1
presents itself and its team; the user validates or adjusts before the org goes live.
This prevents agents from acting autonomously before the user has reviewed their
configuration. See ADR 0006.

After go-live, any agent can be reconfigured directly via `AgentReconfiguration`
(`agents/reconfiguration.py`): the user opens a conversation, requests changes, and a
single extraction LLM call applies them. Structural fields (`domain`, `level`,
`parent_id`) are frozen in v0.1. See ADR 0009.

### The agent loop

> **Status: not implemented yet** (`scheduler/` is empty). The lifecycle above is
> implemented up to go-live (team setup, reconfiguration); the loop below is the
> planned design.

Each agent runs as a persistent `asyncio` coroutine. All loops are started at server
launch and re-created from SQLite on restart (no state is lost).

```text
Each iteration:
  1. Read agent config (AgentSpec) and state (AgentState) from SQLite
  2. If is_paused → sleep 60s → repeat
  3. If outside work_hours → sleep 300s → repeat
  4. Dequeue next task from task queue (if any)
  5. Run think_and_act(agent, task):
       a. Retrieve relevant memories via Chroma similarity search
       b. Build context: system prompt + memories + recent messages
       c. Call LLM via the router
       d. Parse LLM output → messages to send / tasks to delegate /
          deliverables to write / blocking questions to raise
       e. Execute: send messages, write files, update AgentState
  6. Sleep scheduler_interval_seconds → repeat
```

> **Open question — task queue**: step 4 (and VISION §3.3) assume a per-agent,
> priority-ordered task queue, but no `Task` entity exists yet in the models (§3).
> Its lifecycle, priority and links to `AgentState`, `BlockingQuestion` and
> `Deliverable` will be designed in ADR 0011 (planned); this loop will be updated
> accordingly.

### Why asyncio tasks and not APScheduler or Celery

**What APScheduler is**: a Python library that runs jobs on a schedule inside your
process — cron-style rules ("every Monday at 09:00", "on the first day of the
month") or fixed intervals — with optional job persistence in a database, so that
schedules survive a restart.

**What Celery is**: a distributed task queue. The application pushes jobs into a
broker (Redis, RabbitMQ); separate worker processes — possibly on other machines —
pull jobs from the broker and execute them. It is the standard tool for background
jobs in large web applications (sending emails, generating reports), with Celery
Beat for periodic jobs.

**Why neither here**:

- APScheduler's value lies in calendar rules and job persistence. Our schedule is
  an interval (`scheduler_interval_seconds`) plus a daily window (`work_hours`), and
  restart resilience comes from re-creating one loop per `AgentSpec` row at
  startup — a few lines of code.
- Celery adds two services to install and run (a broker and workers) — a
  significant operational burden for a local, single-user application, with no
  benefit at this scale.
- **asyncio tasks** are already FastAPI's runtime. One task per agent is
  lightweight and gives full control over the loop.

**Impact of the asyncio choice**:

- No extra infrastructure: everything runs inside the FastAPI process.
- Pause, resume and work hours are flag checks at the start of each iteration
  (`is_paused` read from SQLite) — no scheduler API to call.
- Agent loops, the dispatcher (§4) and the WebSocket handler share one event loop,
  so messages move between them through in-process queues, with no serialization.

**Trade-offs**:

- **Single process**: if it crashes, every agent loop stops at once. Loops are
  re-created from SQLite on restart; an LLM call in flight at crash time is lost
  (persisted messages, §4, limit the damage).
- **One event loop for every agent**: any blocking or CPU-heavy call stalls all
  agents at once — hence the `async def`-by-default rule for I/O. The workload is
  I/O-bound (waiting on LLMs), which is what asyncio handles well.
- **No scaling across machines**: all agents live in one process on one machine.
- **Calendar rules are hand-written**: anything beyond a daily window (day-of-week
  schedules, multiple windows) must be coded by hand — exactly what APScheduler
  provides for free.
- **To reconsider for a hosted, multi-tenant version**: thousands of agents across
  many users do not fit in one process. A distributed worker model (Celery or
  similar) with an external broker (Redis, §4) would then become relevant.

### Pause and work hours

- `is_paused = True`: the loop detects it within one iteration (at most
  `scheduler_interval_seconds` delay) and enters a 60-second check cycle.
- `work_hours`: a string like `"09:00-18:00"`. The loop checks `datetime.now().time()`
  at each iteration. Outside the window, it sleeps 300 seconds and checks again.
- Global pause (all agents): the UI sends `set_pause` for each agent, or a dedicated
  `/api/org/pause` endpoint sets all `is_paused` flags atomically.

## 6. Real-time communication (WebSockets)

The frontend maintains a single persistent WebSocket connection to the backend. All
real-time updates — agent state changes, new messages, blocking questions,
deliverables — flow through this single channel.

**Why WebSockets and not SSE or polling**:

- **Polling** (frontend asks "anything new?" every N seconds): high latency, wastes
  bandwidth on "nothing new" responses. Unacceptable for a live chat interface.
- **SSE** (Server-Sent Events): the server can push to the client, but it is
  unidirectional. For chat (user types a message → sends it to the agent), a separate
  HTTP request would be needed per user message. Two channels to maintain.
- **WebSockets**: bidirectional, persistent, low-latency. One channel handles both
  server push (agent state changes, new agent messages) and client push (user messages,
  pause commands, blocking question answers). FastAPI supports it natively.

### Message types (server → client)

```python
{"type": "agent_state",       "agent_id": "...", "status": "working", "task": "..."}
{"type": "message",           "conversation_id": "...", "message": {...}}
{"type": "blocking_question", "agent_id": "...", "question": "...", "id": "..."}
{"type": "deliverable",       "deliverable": {...}}
```

### Message types (client → server)

```python
{"type": "user_message",    "to_agent": "...", "content": "..."}
{"type": "blocking_answer", "question_id": "...", "answer": "..."}
{"type": "set_pause",       "agent_id": "...", "paused": true}
```

## 7. Memory architecture

Two layers, both backed by Chroma (local vector database, no server required).

**Per-agent memory**: a namespaced Chroma collection per agent. Only that agent reads
and writes to it. Stores: conversation summaries, task outcomes, learned business
facts.

**Global knowledge base**: one shared Chroma collection. All agents can read it.
Only the Generator Agent (at onboarding) and the COO can write to it. Stores: the
full business context from the interview, shared facts, company-level knowledge.

**Why Chroma for vectors and SQLite for structured data**: Chroma handles embeddings
and similarity search natively (what memories are relevant to *this* query?). SQLite
handles structured queries, joins, and transactional state (which agents exist, what
messages were sent, what deliverables were created). Using one system for both would
mean either losing semantic search or losing relational queries.

**Embeddings**: a small local model via Ollama (e.g. `nomic-embed-text` or
`qwen3-embedding:0.6b`) for full offline support. Cloud embeddings (OpenAI, Voyage)
are an optional enhancement, disabled by default.

**Memory visibility**: the frontend exposes agent memory to the user. Use cases:
understanding why an agent made a decision, correcting a wrong memory, auditing what
the org knows about the business. Two API endpoints:
`GET /api/agents/{id}/memories` and `GET /api/knowledge-base`.

## 8. LLM router

No agent picks its own model. A single `LLMRouter` is the only component that decides
which model handles a given task.

**Why a centralized router**: privacy rules (sensitivity = high → local only, never
cloud) must be enforced consistently. If agents chose their own models, a single
misconfiguration could send sensitive data to a cloud provider. Centralization also
makes cost tracking and routing rule changes easy — one place to update.

```python
class RouterRequest(BaseModel):
    agent_id: str
    task_type: str     # "interview", "planning", "chat", "writing", ...
    sensitivity: str   # "low", "medium", "high"
    complexity: str    # "low", "medium", "high"

class RouterDecision(BaseModel):
    provider: str      # "ollama", "anthropic", "openai", "google"
    model: str         # e.g. "qwen2.5:7b", "claude-opus-4-7", "gpt-4o"
    temperature: float
    max_tokens: int
    reason: str        # logged for traceability
```

### v0.1 routing rules (deterministic)

| Condition | Provider | Rationale |
| --- | --- | --- |
| Generator Agent | Cloud — claude-opus-4-7 | One-shot, highest quality required |
| sensitivity = high | Local Ollama | Privacy: sensitive data never leaves the machine |
| complexity = high | Cloud — claude-sonnet-4-6 | Local models insufficient for complex reasoning |
| All other tasks | Local Ollama | Fast, private, offline-capable, free |

The user can set a preferred cloud provider (Anthropic / OpenAI / Google) in settings.
Per-agent model preferences are respected as hints, overridden only by sensitivity
and complexity rules.

### Concurrency control

The router enforces two configurable limits via `asyncio.Semaphore`:

```python
self._local_semaphore = asyncio.Semaphore(settings.MAX_CONCURRENT_LOCAL_REQUESTS)
self._cloud_semaphore = asyncio.Semaphore(settings.MAX_CONCURRENT_CLOUD_REQUESTS)

async def call(self, request: RouterRequest) -> str:
    decision = self.route(request)
    if decision.provider == "ollama":
        async with self._local_semaphore:   # waits if limit reached
            return await self._call_ollama(decision)
    else:
        async with self._cloud_semaphore:   # waits if limit reached
            return await self._call_cloud(decision)
```

**`MAX_CONCURRENT_LOCAL_REQUESTS`** (default: `1`): max parallel inference calls sent
to Ollama. Should be ≤ `OLLAMA_NUM_PARALLEL` on the Ollama server. Users with large
unified memory (32 GB+) can increase both to run multiple agents simultaneously.

**`MAX_CONCURRENT_CLOUD_REQUESTS`** (default: `3`): max parallel cloud API calls
across all providers. Keep low to stay within rate limits; increase on high-tier API
plans.

A waiting agent does not block — it suspends its asyncio coroutine until a slot opens.
No timeouts, no errors, just queued inference.

### Startup staggering

To avoid a burst of simultaneous LLM calls at server startup (all agent loops waking
up at second 0), each agent loop applies a random initial delay of 0–60 seconds before
its first iteration. This is applied once at startup; subsequent intervals are
deterministic (`scheduler_interval_seconds`).

### v0.2+

Cost-aware routing (track token spend per provider per agent), latency-aware routing,
and user-configurable routing rules via natural language configuration.

## 9. Prompt management

All prompts live in `backend/adjents/prompts/`. Loaded at runtime by a `PromptLoader`
utility — never hard-coded in Python source files.

**Why external prompt files**: prompts need to be iterated on independently of code.
A product improvement (better interview questions, better think-and-act reasoning) should
not require a code change, a review, or a deployment. Prompts as `.md` files are:

- Editable without touching Python
- Version-controlled in git (diffs are readable)
- Testable in isolation (load the file, render with test variables, inspect output)
- Reviewable as documentation by non-engineers

### Naming convention

```text
prompts/<agent_type>/<purpose>.md

prompts/generator/interview.md
prompts/generator/org_generation.md
prompts/coo/daily_planning.md
prompts/agent/think_and_act.md
prompts/agent/memory_summary.md
```

### YAML frontmatter

```yaml
---
version: 1
description: "Generator Agent onboarding interview"
model_hint: "claude-opus-4-7"
---
```

### How prompts are loaded

`PromptLoader` reads all `.md` files at server startup and caches them in memory.
At runtime, any module can request a rendered prompt:

```python
loader = PromptLoader("backend/adjents/prompts/")

# Raw content
prompt = loader.get("generator/interview")

# With template variables substituted
prompt = loader.render("agent/think_and_act",
                       agent_name="Alex",
                       responsibilities=["Handle invoicing", ...])
```

### When prompts are loaded

| Event | Prompt |
| --- | --- |
| Onboarding interview starts | `generator/interview` |
| Generator produces the org | `generator/org_generation` |
| Post-generation team setup: agent introduction | `agent/intro` |
| Post-generation team setup: extract adjustments | `agent/extract_agent_adjustments` |
| Direct agent reconfiguration: extract adjustments | `agent/extract_agent_adjustments` |
| Every `think_and_act` iteration | `agent/think_and_act` |
| Agent summarizes its memories | `agent/memory_summary` |
| COO plans the day | `coo/daily_planning` |

`agent/extract_agent_adjustments` is shared by both `TeamSetupOrchestrator` and
`AgentReconfiguration`. The prompt reads a full conversation transcript and returns a
JSON object with `agent_updates`. A retry loop (max 3 attempts) handles malformed JSON
responses. See ADR 0008 for the full extraction pattern design.

## 10. Deliverables storage

Agents write outputs to `data/outputs/` in a structured directory tree:

```text
data/outputs/
├── <agent_id>/
│   ├── 2025-05-18_client-proposal.md
│   ├── 2025-05-18_invoice-draft.txt
│   └── ...
└── projects/
    └── <project_id>/
        ├── 2025-05-20_website-copy.md
        └── ...
```

Every file written is registered as a `Deliverable` record in SQLite. The UI reads
from SQLite to list deliverables and opens files from their local path on demand.

File writes outside `data/` are not permitted in v0.1.

## 11. Frontend architecture

### Technology choices

| Part | Technology | Why |
| --- | --- | --- |
| Framework | React 19 + TypeScript | Component model, large ecosystem, type safety |
| Build tool | Vite | Near-instant dev server with hot reload; faster than Webpack |
| Styling | Tailwind CSS | Utility-first; no custom CSS files to maintain |
| UI components | shadcn/ui | Pre-built accessible components; code lives in the project (no black box) |
| 2D workspace | PixiJS + @pixi/react | WebGL rendering; animation-ready from day 1 (see below) |
| Server state | TanStack Query | Handles caching, background refresh, and loading states for API data |
| Client state | Zustand | Lightweight store for UI state and WebSocket data; no Redux boilerplate |
| Real-time | Native WebSocket API | Built into all browsers; no library needed |

**Vite** is the compilation and development tool. It transforms TypeScript + React
into browser-compatible JavaScript and provides a dev server where changes appear
instantly without page reload. The user never interacts with it directly.

**TanStack Query** manages data fetched from the REST API (agent list, conversation
history, deliverables). Instead of writing `fetch()` + manual caching in every
component, TanStack Query provides a declarative `useQuery` hook that handles
caching, stale-data refresh, and error states automatically.

**Zustand** manages client-side UI state that does not come from the API: which agent
is selected, whether the chat panel is open, and the real-time agent states received
via WebSocket. It is the bridge between the WebSocket stream and both the React
components and the PixiJS render loop.

### Why PixiJS from v0.1 (not React + CSS first)

An earlier option was React + CSS for v0.1 (static sprites), then migrate to PixiJS
in v0.3 for animations. We rejected this because the migration would require a full
rewrite of the workspace component (~300 lines) with no code reuse between the two
approaches. Doing the work twice costs more than starting with PixiJS and accepting
its slightly steeper initial setup. Static sprites work fine in PixiJS — we simply
add animations in v0.3 without changing the architecture.

PixiJS renders the 2D house canvas. React renders everything else. They share state
via Zustand.

### Overall layout

The application has two top-level views:

- **Onboarding**: full-screen conversation with the Generator Agent
- **Workspace**: the main operational interface after onboarding

The Workspace is a near-fullscreen PixiJS canvas with on-demand overlays:

```text
┌─────────────────────────────────────────────────────────────┐
│ [Adjents logo]   [Org chart]  [Deliverables]  [🔔 3]  [⏸] │ ← top bar (always visible)
├─────────────────────────────────────────────────────────────┤
│                                                             │
│                                                             │
│                   2D House  (PixiJS canvas)                 │
│             scrollable / zoomable / near-fullscreen         │
│                                                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**On-demand overlays (hidden by default, opened by user action):**

| Element | Trigger | Behaviour |
| --- | --- | --- |
| Chat panel | Click on an agent | Slide-in panel on the right |
| Org chart | Click "Org chart" in top bar | Modal/popup |
| Deliverables | Click "Deliverables" in top bar | Dedicated side panel or full view |
| Notifications + blocking questions | Click 🔔 badge | Slide-in panel listing pending questions |

The house canvas is scrollable and zoomable to accommodate any number of rooms and
agents.

### PixiJS ↔ React data flow

```text
WebSocket message
      │
      ▼
Zustand store  (agent states, conversations, notifications)
      │
      ├── React components  (top bar, chat panel, org chart, deliverables)
      └── PixiJS render loop  (house, rooms, sprites, visual states)
```

In v0.1, each agent has one static sprite per `AgentStatus` value. The PixiJS render
loop swaps sprites when the Zustand store updates. Animations are added in v0.3 by
replacing static sprite swaps with tweened transitions — no architectural change.

### State principle

SQLite is the source of truth. The frontend never holds business state for more than
one WebSocket sync cycle without it being backed by a server record.

## 12. Testing strategy

### Backend

- **pytest** + **pytest-asyncio** for all async tests
- **Pydantic models**: each model gets a test for valid construction and at least one
  invalid case (type error, missing field)
- **FastAPI endpoints**: each endpoint gets a happy-path test and at least one
  error-path test (4xx response)
- **WebSocket handlers**: tested with `pytest-asyncio` WebSocket test client
- **Generator Agent**: golden-file tests — given a canonical business description,
  the LLM output (mocked) must produce an org matching the expected structure
- **Agent loop**: tested with a fake clock and a mock LLM to verify that pause/resume,
  work hours, and message triggers behave correctly

### Frontend

- **vitest** + **React Testing Library** for component tests
- Key interactions tested: onboarding flow, agent click → chat opens, blocking
  question answered → notification clears

### Linting and type checking (run on every commit and in CI)

| Tool | Scope | Command |
| --- | --- | --- |
| **Ruff** | Python lint + format | `ruff check . && ruff format --check .` |
| **mypy** (strict) | Python types | `mypy --strict adjents/` (from `backend/`) |
| **ESLint** | TypeScript/React lint | `pnpm lint` |
| **Prettier** | TypeScript/React format | `pnpm format:check` |
| **tsc** | TypeScript types | `pnpm typecheck` (`tsc --noEmit`) |

CI runs `lint → typecheck → test` on every PR. A PR cannot be merged if any step fails.

## 13. Deployment (v0.1)

Local-only. The user runs:

```bash
make install   # uv sync + pnpm install
make dev       # FastAPI on :8000 + Vite on :5173
```

Vite proxies `/api` and `/ws` paths to FastAPI so the frontend makes no cross-origin
requests during development.

Ollama must be running separately (`ollama serve`) with at least one model pulled.

Public deployment and packaging for non-technical users are out of scope for v0.1.
